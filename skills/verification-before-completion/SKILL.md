# Verification Before Completion

## Overview

在声称已完成、已修复、可正常工作、测试已通过之前，先验证，再下结论。

这个 skill 用来约束交付前的最后一步。所有完成声明都必须建立在当前回合的真实验证结果之上，而不是经验、直觉、记忆，或看起来应该没问题的推测。

## When to Use

在下面这些场景中使用：

- 准备回复用户已经修好或已经完成
- 准备说测试通过、构建通过、类型检查通过
- 准备提交 commit、创建 PR、请求验收、移交工作
- 刚做完代码、配置、文档修改，想总结结果
- 准备使用 fixed、done、passing、working 这类结论性措辞

不要用于这些场景：

- 纯讨论、纯设计、纯排查，还没有实际改动
- 明确只是给出初步判断，还没进入交付阶段
- 用户只要求分析原因，没有要求确认修复结果

## Core Principle

没有验证结果，就没有完成。

即使字面上没有说已完成，但语义上在暗示已经没问题，也算违规。比如：

- 现在应该可以了
- 理论上已经修好了
- 这部分没问题了
- 可以放心提交

这些话都必须先有验证支撑。

## Verification Workflow

按下面顺序执行，除非任务本身明确不适用。

### 1. 确认你要证明什么

在验证前，先把目标说清楚：

- 修复的是哪一个 bug
- 完成的是哪一项功能
- 通过的是哪一类检查
- 对用户要承诺的结论是什么

如果连要证明什么都说不清，就还不该进入完成确认阶段。

### 2. 选择最接近真实风险的验证

不要为了跑过某个命令而验证。验证方式要贴近改动带来的风险。

优先级参考：

- 代码逻辑改动：运行相关测试
- 类型或接口改动：运行 diagnostics、typecheck
- 构建链路改动：运行 build
- 用户可见行为改动：实际运行关键路径、手动验证或浏览器验证
- 配置改动：验证配置被正确读取或命令实际生效
- 文档改动：检查内容、路径、链接、结构是否正确

### 3. 先做局部验证，再决定是否升级

建议顺序：

1. 改动文件级别检查
2. 最相关的局部测试或诊断
3. 必要时再升级到更高层级验证，例如 typecheck、build、integration
4. 用户可见行为需要实际走通关键路径

不是所有任务都要跑全套，但每个完成结论都至少要有一个直接相关的验证动作。

### 4. 记录实际结果，而不是脑补结果

记录时只允许三类状态：

- 通过：已执行，结果明确成功
- 失败：已执行，结果明确失败
- 未验证：没有执行，或结果不足以支撑结论

禁止把下面这些话当成结果：

- 应该通过
- 大概率没问题
- 我没看到异常，所以算通过
- 理论上不会出错

### 5. 用结果约束结论

结论必须和验证结果严格一致：

- 只验证了局部测试：只能说相关局部验证已通过
- 没跑 build：不能说整体已完成且可交付
- 没手动验证用户路径：不能说用户侧行为已确认正常
- 有失败项：不能用已修复收尾，除非明确说明失败与范围

## Minimum Verification Matrix

| 变更类型 | 最低建议验证 |
|---|---|
| 单文件代码修复 | 相关测试或 diagnostics |
| 多文件逻辑改动 | 相关测试加 diagnostics |
| 类型或接口改动 | diagnostics 或 typecheck |
| 构建流程改动 | build |
| UI 或用户可见行为 | 实际交互验证 |
| 文档改动 | 内容与结构检查 |
| 重构 | diagnostics 加相关测试 |

## Reporting Format

交付前的汇报至少应包含下面几项：

- 已做改动：改了什么
- 已验证：执行了哪些命令或工具检查
- 结果：通过、失败、部分通过
- 未验证项：哪些还没验证
- 风险或后续建议：剩余不确定性是什么

可直接使用这个模板：

```markdown
- 已做改动：...
- 已验证：...
- 结果：通过 / 失败 / 部分通过
- 未验证项：...
- 风险或后续建议：...
```

## Red Flags

出现下面这些念头时，停止下结论，先去验证：

- 改动很小，应该不用测
- LSP 没报错，大概就行
- 我很确定这能工作
- 先告诉用户完成了，之后再补测
- 测试太慢，先跳过
- 这个问题太明显了，不用验证也知道修好了

## Rationalization Table

| 借口 | 现实 |
|---|---|
| 改动太小，不值得测 | 小改动同样会破坏边界条件 |
| 我已经读过代码了，应该没问题 | 阅读代码不是验证执行结果 |
| 这只是类型改动，不会影响行为 | 类型改动同样可能破坏调用链 |
| 局部测过了，所以整体也没问题 | 局部通过不代表系统级通过 |
| 先说完成，等会再补验证 | 这是把不确定性伪装成结论 |

## Common Mistakes

### 1. 把 diagnostics 当成功能验证

lsp_diagnostics 很重要，但它只能说明静态层面没有明显错误，不能证明运行行为正确。

### 2. 只跑了不相关测试

测试必须和本次改动直接相关。跑了一组无关测试，不足以支撑这个修复已经生效。

### 3. 省略未验证项

没有验证的内容可以存在，但必须明确说出来，不能隐去。

### 4. 结论超出证据范围

证据只覆盖一部分，就只能给出部分结论。不要把局部没问题扩大成整体已经完成。

## Completion Gate

只有同时满足下面条件，才可以使用完成、修复好了、通过了这类结论：

- 相关改动已保存
- 至少一个与任务直接相关的验证已实际执行
- 没有未说明的失败
- 回复内容与工具输出一致
- 结论没有超出证据覆盖范围
